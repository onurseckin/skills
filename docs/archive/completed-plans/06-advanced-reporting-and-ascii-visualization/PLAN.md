# Plan 6: Advanced ASCII Reporting Architecture & Nomenclature Simplification

## 1. Context & Problem Statement

The current diagnostic reporting system suffers from two core issues:

1. **Obsolete "Unified" Nomenclature:**
   - Files and exports retain redundant `unified` prefixes (e.g. `reporting/unified.ts`, `cli/commands/unified-reporting.ts`, `generateUnifiedReport`, `reportUnifiedCommand`).
   - The command name is already simply `report`; the internal implementation should mirror this directly (`reporting/report.ts`, `cli/commands/report.ts`).

2. **Unstructured & Missing Visual Agent Hierarchy:**
   - Reports currently render a flat markdown table of agents and an unstructured dump of wave lanes.
   - When inspecting a long-running long-task, users cannot immediately visualize the **Active Agent Hierarchy Tree** (who is Tier 1 Orchestrator, who is Tier 2 Coordinator, which Tier 3 Implementers are leased to which tasks, and who is validating them).
   - Other system reports (`mind:pulse`, `doctor`, `dag`, `defect:audit`) lack a unified aesthetic visual language.

## 3. Design Options Analysis

### Option A: Pure Modular ASCII Renderers (Recommended)

- **Architecture**:
  - `olt/scripts/src/reporting/ascii/agent-tree.ts`: Generates the parent-child agent hierarchy tree.
  - `olt/scripts/src/reporting/ascii/dag-tree.ts`: Generates the Sugiyama topological wave graph.
  - `olt/scripts/src/reporting/ascii/table-formatter.ts`: Formats clean ASCII/Unicode boxed tables.
  - `olt/scripts/src/reporting/report.ts`: Orchestrates all reporting data into a cohesive markdown document.
  - `olt/scripts/src/cli/commands/report.ts`: Clean CLI command handler.
- **Pros**:
  - Clean separation of concerns; zero code bloat.
  - Each renderer is independently unit-testable with deterministic snapshots.
  - Fully reusable across `report`, `mind:pulse`, `doctor`, `dag`, and `meta-audit`.
- **Cons**:
  - Requires creating 2-3 focused helper modules.

### Option B: Monolithic Single-File String Builder

- **Architecture**:
  - Put all rendering logic inside a single 1000+ line `reporting/report.ts` file.
- **Pros**:
  - Fewer files created.
- **Cons**:
  - Violates single-responsibility principle; harder to test and maintain.

## 4. Implementation Steps & Acceptance Criteria

1. **Step 1: Delete Redundant "Unified" Word**:
   - Rename `olt/scripts/src/reporting/unified.ts` $\rightarrow$ `olt/scripts/src/reporting/report.ts`.
   - Rename `olt/scripts/src/cli/commands/unified-reporting.ts` $\rightarrow$ `olt/scripts/src/cli/commands/report.ts`.
   - Rename all `Unified*` types to clean canonical names (`ReportSummary`, `AgentHierarchyRow`, `ReportPhaseSummary`).

2. **Step 2: Implement `ascii/agent-tree.ts`**:
   - Parse `state.agents` array and resolve parent-child relationships via `parent_agent_id`.
   - Render top-down ASCII tree with Tier badges (`[Tier 1: Orchestrator]`, `[Tier 2: Coordinator]`, `[Tier 3: Implementer]`), status, host, and active task leases.

3. **Step 3: Harmonize Report Formatting Across All Tools**:
   - Standardize ASCII box frames and headers across `report`, `dag`, `doctor`, `mind:pulse`, and `defect:audit`.

4. **Step 4: Verification & Test Suite**:
   - Update `tests/unit/reporting/` tests to verify the new clean renderers.
   - Verify `bun run typecheck` exits 0 with 0 `any` and 0 compiler suppressions.
   - Run `bun harness.ts report` and verify clean, aesthetic terminal rendering.
